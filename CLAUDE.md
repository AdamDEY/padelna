# Padelna

Padelna is a social app for padel players: find and create matches at the right level, book courts, rate players and confirm scores. A player's level (1–7 scale) and trust signals (confirmed scores, reputation) are the core of the product. Launch market is Tunisia (`+216` phone numbers); the UI ships in English first, with French and Arabic (right-to-left) planned.

## Stack

- Expo SDK 58, React Native 0.88, React 19, TypeScript (strict), Expo Router (typed routes)
- **HeroUI Native** (`heroui-native`) for UI components, styled with **Uniwind** (Tailwind CSS v4 for React Native)
- Reanimated 4, Gesture Handler 3, `@gorhom/bottom-sheet`
- Package manager: **npm** (`package-lock.json`). Use `npx`, and `npx expo install <pkg>` to add packages.
- iOS and Android only. HeroUI Native is not supported on web, so don't build or test for web.

## Commands

```bash
npm run ios                 # native build + run on the iOS Simulator (needed after any native dependency change)
npx expo start --dev-client # start Metro for an existing dev build
npx expo start --dev-client --clear  # after changing metro.config.js or when styles look stale
npx tsc --noEmit            # typecheck
npx expo lint               # lint
```

This is a development build, not Expo Go. CocoaPods needs a UTF-8 locale (`LANG=en_US.UTF-8`, already set in `~/.zshrc`).

## Project layout

- `src/app/` — routes only (Expo Router). Every file is a screen; `_layout.tsx` files are navigators.
- `src/components/` — shared components, built on top of HeroUI components. One component per file, kebab-case file name, named export (`export function TeamPicker`).
- `src/data/mock.ts` — all mock data until the backend exists (see "Data" below).
- `src/types/` — domain types (`player.ts`, `match.ts`, `club.ts`, `profile.ts`, `post.ts`).
- `src/lib/` — pure helpers with no UI (`format-date.ts`, `level-fit.ts`, `validation.ts`, `error-message.ts`) and the Supabase client (`supabase.ts`).
- `src/repositories/` — the only code that talks to Supabase (`auth-repository.ts`, `profile-repository.ts`, `match-repository.ts`, `player-repository.ts`). One file per area; functions throw on error. Screens and hooks never import `supabase` directly.
- `src/hooks/` — React Query hooks that wrap repository functions (`useMyProfile.ts`). Hook files are named in camelCase after the hook, not kebab-case. `src/lib/query-client.ts` holds the shared `QueryClient`.
- `src/global.css` — Tailwind/Uniwind/HeroUI entry and **the single place where design tokens live** (as HeroUI theme variables).
- `src/uniwind-types.d.ts` — generated by Uniwind when Metro starts; don't edit by hand.
- `example/` — the old Expo template, git-ignored and excluded from typecheck. Use it for reference only; never import from it.
- `ios/` — generated (CNG). Configure native behaviour in `app.json` / config plugins instead.
- Import from `src` with the `@/` alias (`@/components/...`).

## UI rules

`design.md` is the source of truth for colours, type, spacing, radii and component specs. HeroUI provides the components. Combine them like this:

0. **Every screen is built on `Page`** (`src/components/page.tsx`): `<Page variant="app" | "auth">` with `Page.Header` (back button, compact title, right-side `IconButton`s), `Page.Body` (scrolls by default), `Page.Title` (H1 with optional eyebrow and description) and `Page.Footer` (the pinned primary action). `Page` owns the background, safe areas, side margins and keyboard handling, so screens never set those themselves. Use `IconButton` (`src/components/icon-button.tsx`) for round icon-only buttons.
1. **Use a HeroUI component first.** Before building any control (button, input, chip, card, segmented control, bottom sheet, dialog, avatar, toast, etc.), check whether HeroUI Native has it and use it, styled to match `design.md`. Only build a custom component when HeroUI has nothing suitable (e.g. level chip, score grid, court placeholder), and put it in `src/components/`.
2. **Style with Uniwind `className`**, not `StyleSheet.create` or inline style objects. Inline styles are fine only for dynamic values (animations, computed sizes).
3. **Never hard-code hex colours in components.** Map `design.md` colours onto HeroUI's theme variables in `src/global.css` (`--background`, `--surface`, `--foreground`, `--accent`, `--success`, `--warning`, `--danger`, `--border`, `--field-*`, …). Add Padelna-only colours (lime, attention, avatar tints, …) as new variables plus `@theme inline` mappings, so they can be used as Tailwind classes (`bg-lime-soft`, `text-ink-2`).
4. **Light theme only** for now. `design.md` defines no dark palette, so don't add `dark:` variants.
5. **Font is Nunito**, loaded in `src/app/_layout.tsx`. Each weight is its own font family on native, so pick the weight with these classes, never `fontWeight`: `font-normal` (400), `font-medium` (600), `font-semibold` (700), `font-bold` (800), `font-black` (900). Hierarchy comes from weight (800–900), not from extra colours.
6. **Spacing and radii** follow the `design.md` scale: 20 px screen margins (24 px on auth/setup/onboarding), cards with radius 20–24 and padding 14–16, inputs 52 px tall with radius 14, primary buttons 54–56 px tall with radius 16–18.
7. **One primary (blue) button per screen**, usually pinned 34 px from the bottom.
8. **No gradients, emoji or card shadows.** Shadows are only for floating elements (FAB, the centre Create button).
9. **Icons** come from `lucide-react-native`, always rendered through `<Icon as={Bell} color="muted" />` (`src/components/icon.tsx`). It applies the 1.8 px stroke and takes a theme colour name instead of a hex value.
10. **Main tabs use the native tab bar**: `NativeTabs` from `expo-router/native-tabs` in `src/app/(tabs)/_layout.tsx` (Home, Matches, Community, Players, Profile). Icons are SF Symbols (`sf`) on iOS and Material Symbols (`md`) on Android. Don't recreate the Liquid Glass look by hand. On Android the native bar is Material, so `(tabs)/_layout.android.tsx` uses JS `Tabs` with `FloatingTabBar` (design.md "Glass tab bar") instead; it gives tab screens a bottom safe-area inset that includes the bar, like iOS does, so screens need no Android-only padding. Screens that open on top of the tabs (details, settings) go outside `(tabs)` so the root `Stack` pushes them.

## Code style

Match the existing files; read a neighbouring component before writing a new one.

- Function components with a `XxxProps` type above them; destructure props with defaults in the signature. Short JSDoc on the component (`/** What it is (design.md "Name"). */`) and on non-obvious props.
- Comments are sparse and explain *why* (a design constraint, a platform workaround), not what the code does.
- Use `cn()` from `heroui-native` for conditional classes. Variant maps are `const tones = { ... } as const` objects keyed by name.
- Name magic numbers as `UPPER_CASE` constants at the top of the file, with a comment when they come from the design (`const SHEET_OVERLAP = 36; // How far the sheet slides over the court`).
- Theme colours that a native API needs as a value (tab bar, SVG stroke, pickers) come from `useCSSVariable("--color-…")` from `uniwind`, never hex.
- Use `Fragment` instead of `display: contents` (unsupported on native). Uniwind `className` cannot be a function; use `style` for pressed states.
- Validation: track a `submitted` flag, compute `xxxError = submitted && !valid`, pass `isInvalid` to HeroUI `TextField` with a `FieldError`. Actions that need the backend show a toast via `useToast()` and say what will happen once the API exists (`// Nothing is saved yet; the API will …`).
- Typed routes: keep `href`s and `pathname`s valid so `tsc` catches broken links.

## HeroUI and native gotchas (learned the hard way)

- Inside a HeroUI `BottomSheet`, use `Pressable` and `ScrollView` from `react-native-gesture-handler`, not from `react-native`, or taps and scrolling are swallowed. HeroUI `Tabs` gets no taps there, so use `SegmentedControl`.
- Native SwiftUI pickers (date/time) render blank inside a sheet unless it uses `<BottomSheet.Portal disableFullWindowOverlay>`.
- `Select` inside a sheet needs a custom trigger; long option lists go in a gesture-handler `ScrollView` with a `maxHeight` (see `create-match-sheet.tsx`).
- HeroUI `Label` only accepts plain text; put extras like "(optional)" in a `Text` next to it.
- Adding a native module (e.g. `expo-image-picker`) needs a rebuild: `LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8 npx expo run:ios --no-bundler --device "iPhone 17"` (the locale is required by CocoaPods; non-interactive shells don't load `~/.zshrc`).
- Adding or changing a config plugin in `app.json` (entitlements, `googleServicesFile`, notification icon) needs `npx expo prebuild --platform ios|android` first; `expo run` alone doesn't re-apply it to the existing `ios/` and `android/`.
- Android builds need JDK 17: the Mac's default Java is too new for Gradle. Run `JAVA_HOME=/Library/Java/JavaVirtualMachines/zulu-17.jdk/Contents/Home npx expo run:android --no-bundler` on the `Pixel_10` emulator.
- Heroes drawn for a 44 pt status bar must offset by `insets.top - 44` (see `sign-in.tsx`) so they don't collide with taller status bars.
- In the Simulator, iOS's "Strong Password" overlay blocks typing into `textContentType="newPassword"` fields (no Keychain). That's a simulator limitation; keep the content type.

## Product rules

- Padel is 2 vs 2: matches have 4 seats, seats 1–2 vs 3–4.
- **Every match lasts 90 minutes.** Start times are in **half-hour steps** (07:00–23:00), picked from a dropdown.
- Match type is Friendly or Competitive. Friendly results don't change your level; competitive results count toward level. Show that as a hint when creating a match, and use **different colours** for friendly vs competitive result cards/scoreboards.
- A match's court is either booked (show club + court, green "Court booked") or not yet (sand "Not booked yet" note asking the host to add the club and court later).
- **Scores need one player from each team.** Once a match is over the host adds the score (set by set, best of three); one player from the other team confirms it or enters the real score, which a player from the host's team then confirms. A score nobody confirms within 48 hours expires and never counts. The rules live in the `submit_score` / `confirm_score` database functions and `src/lib/padel-score.ts`.
- **Team photos are shared with the community**: the host adds one with the score (uploading it means sharing it). It lives in the `match-photos` bucket, readable by any signed-in player, shown through short-lived signed URLs (`useMatchPhotoUrl`).
- **Community** feeds are all confirmed matches, newest confirmation first, from one internal `community_feed` database function (a match shows in **one tab only**: Friends takes every match you or a friend played, **My clubs** and **All Tunisia** leave those out and keep their Connect buttons): **Friends** (you or a friend played, `get_friends_feed`), **My clubs** (at your clubs, filter by club, `get_clubs_feed`, with the `get_clubs_week` banner) and **All Tunisia** (every club, filter by club city, `get_tunisia_feed` / `get_community_cities`, with `get_rising_players`: biggest level gain from matches in 30 days, hidden when nobody has one). Hooks are in `useFeed.ts`; `CommunityFeed` renders a feed and `src/lib/feed-post.ts` turns a match into a card told from your side.
- **Connections are two-way**: a player sends a request and the other accepts (`request_connection` / `respond_to_connection`). A match "played" is one that's over and had all 4 seats taken; a club becomes one of **your clubs** once you've played there. The Players tab suggests people you played with and players within half a level of you at your clubs.
- **Player ratings (-2 to +2 per player, `player_ratings`) only matter in competitive matches.** Friendly matches have no rating step (`isRatingOpen` / `playersToRate` return nothing for them and `submit_ratings` rejects them). When rating, players can also pick up to 5 positive tags per player from a fixed list (`src/data/player-tags.ts`, same list as `c_tags` in `submit_ratings`; names in `playerTags` in the locale files). They are anonymous like the ratings and show as **What players say** (counts only) on the Profile and in the player sheet, via `get_player_tags`. There is no Reviews row or review count on the profile. Ratings are stored as given, so the level calculation can be calibrated later: **TODO, once the level quiz is set up with the coaches, agree how much each rating moves a level** and set the constants in `settle_match_levels` (`c_rating_step`, `c_min_raters`, `c_max_change`; today's values are placeholders). Until then, ratings are collected but don't move levels (`c_rating_step` = 0 in migration `20261106100000_friendly_matches_not_rated.sql`); past matches can be recomputed from the stored ratings.
- **Tournaments** are run by the admin; only group stage + knockout can be joined from the app so far (Americano opens read-only). A tournament opens once the admin sets a capacity. Every pair is two app players: you invite a friend, the spot is held for 24 hours until they accept, and when full the pair goes on the waitlist and moves up automatically. A player with no partner joins the partner list and the admin pairs them. Each player must fit the level range and category when joining from the app; the admin can override. The fee is per team, paid at the club desk. Results don't change levels. An invite past its 24 hours is removed by the `expire-tournament-invites` job within a minute: the captain is told and the oldest waiting pair moves up. A player on the partner list can also receive an invite; the invite wins as their entry until they answer it. An invite's notification is removed once it can't be answered any more. Tournament pushes have their own setting. Once a tournament is live, a player in a match sends its score from the app (`submit_tournament_score`, two sets to 4 and a super tie-break); it shows as waiting and only counts once the organiser confirms or corrects it in the dashboard. Matches have no time or court yet, so the live screens show rounds instead. **Individual Americano** can be joined too: players join alone (`join_tournament_solo`, waitlist when full) or the organiser adds them in the dashboard; the capacity is a multiple of 4 and only confirmed players are drawn at the start. Once live, `tournament/[id]` shows `AmericanoLiveView` (round, my partner and opponents, next round, leaderboard, my rounds). Scores use the tournament's mode (one set to 4 games, or a super tie-break to 10); a player in the match saves it with `submit_americano_score` and it counts straight away, and they or the organiser can correct it. There is no round timer. The rules live in `join_tournament` and friends (migrations `20261109140000_tournament_registration.sql`, `20261109160000_tournament_registration_fixes.sql` `20261109180000_tournament_polish.sql`, `20261109200000_tournament_live.sql` and `20261109210000_americano_individual.sql`).
- Level fit uses `src/lib/level-fit.ts` (great / good / above / below); outside your range you "Ask to join" instead of "Join match".
- Connect buttons use the light blue **secondary** button everywhere.
- Prices are per player, in TND. Phone numbers are Tunisian (`+216`, 8 digits).

## Clubs

Clubs are real data from Supabase (`clubs`, `courts`, `club_hours`, `club_photos`, filled in from the admin dashboard), read by `src/repositories/club-repository.ts` and `src/hooks/useClubs.ts`. `useClubCards` adds the open-match count, "your club" and the distance on top; distance needs the player's location (`useMyLocation`, `expo-location`) and a club with a map pin, so it's left out otherwise. Drafts are hidden by the database; only `published` clubs can host new matches. **Club reviews** live in `club_reviews` (migration `20261106160000_club_reviews.sql`), read by `club-review-repository.ts` and `useClubReviews.ts` (`get_club_ratings`, `get_club_reviews`, `submit_club_review`). Only players who have played a full match at the club can review it, one review per player per club (sending again replaces it). The club screen has a "Rate the club" button (`useRateClub` + `RateClubSheet`), the summary with popular tags, the latest two reviews and "See all", which opens `club/[id]/reviews` (topic filter, score per court, every review). Aspects are in `src/data/club-review-aspects.ts`, tags in `src/data/club-review-tags.ts` (same list as `c_tags` in `submit_club_review`). There is no "Helpful" or club reply yet. Club photos aren't shown yet either (the court-line placeholder stands in); `club_photos` rows are in a private bucket and would need signed URLs.

## Profile stats

The Profile's numbers are real: `get_my_stats` (`stats-repository.ts`, `useMyStats`) counts matches with a **confirmed score** (friendly and competitive). Win rate, streak, level over the last 6 months (`level_history`), win rate by opponent level (today's levels, ±0.25 = same) and by set, and best partners (2+ matches together) show only from **5 scored matches** (`STATS_MIN_MATCHES` in `src/lib/profile-stats.ts`); before that the hero shows dashes and `NewPlayerCards` shows placeholders. There is no "by side" because matches don't record which side of the court a player stood on. A coach evaluation (admin app) sets the player's level (`level_history.cause = 'coach'`) and shows as a badge plus the **Coach evaluation** card.

## Data

Most of the app now reads from Supabase (see the repositories). What is still mock lives in `src/data/mock.ts` (dates are relative to today, `me` is the signed-in player with `level: myLevel`), typed with `src/types/`. ## Workflow

Follow this loop for every piece of work:

1. **Branch from `dev`**: `git checkout dev && git pull`, then `git checkout -b feature/<screen-or-feature>` (or `fix/<thing>` for fixes). `main` is not used for day-to-day work; `dev` is the integration branch.
2. **Build it** following the design artboard and the rules above, reusing shared components.
3. **Check it in the iOS Simulator** (iPhone 17): launch with Metro running, drive it with taps and screenshots, test the states (empty, errors, success, links/back). Deep links use `com.padelna.app:///<route>`.
4. Run `npx tsc --noEmit` and `npx expo lint`.
5. **Report and stop.** Summarise what was built and anything not verified. **Don't commit, push or open a PR until the user asks.**
6. When the user says "commit, create the PR and merge": commit with a short imperative subject ("Add Match detail screen") and a body explaining what and why, push the branch, `gh pr create --base dev` with a Summary / Notes / Test plan body, merge with `gh pr merge --merge`, then `git checkout dev && git pull`.

The repo is `AdamDEY/padelna` on GitHub; there is no CI.

## Accessibility and copy

- Touch targets at least 44 px. Body text never below 13 px, labels never below 11 px.
- Every input has a visible label. Icon-only buttons get an `accessibilityLabel`.
- Colour is never the only signal: selected states add a border or tick, warnings add an icon, wins/losses add W/L.
- Keep text out of images and leave room for longer French words. Prefer `start`/`end` (`ps-*`, `pe-*`, `ms-*`, `me-*`) over `left`/`right` so layouts flip for Arabic.
- Copy is short, warm and direct ("Let's play", "Book your court first"). "Coach verified" (badge + level) is shown only for a player with a coach evaluation (`get_coach_verification`); a level built only from the quiz and matches is never called verified.
